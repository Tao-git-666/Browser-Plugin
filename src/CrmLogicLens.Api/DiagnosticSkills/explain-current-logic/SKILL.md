## 取证顺序

先明确用户问的是按钮、字段、窗体加载还是保存动作；优先用当前实体元数据和显示名定位对象，再沿实际绑定关系追踪。名称相同而节点不同的对象不能合并。只读取与问题直接相关的脚本或插件实现，不把搜索命中清单当成业务流程。

从入口说明触发时机、条件来源、执行动作和影响范围。跟进已发现的公共函数；代码明确调用自定义 API 时解析实际操作和实现；落到当前实体写入时才列相关插件步骤。技术标识必须来自工具返回，不编造函数、实体或证据节点。

## 场景与处理

| 用户意图 | 处理方式 |
| --- | --- |
| 按钮有什么用 | 说明点击条件、是否保存/调用接口/打开页面及可见效果；不能仅按按钮标签解释。 |
| 页面打开后会发生什么 | 沿 OnLoad 与实际初始化函数说明赋值、显隐和加载数据；没有调用关系的函数不能列入执行顺序。 |
| 字段变化影响什么 | 沿 OnChange 的实际目标字段、校验和请求解释；发现格式或自动赋值问题时重新匹配 field-value-rules。 |
| 保存会影响哪些数据 | 区分客户端校验、主记录事务和关联异步操作；不把同实体所有插件都称为必定执行。 |
| 同一操作为何结果不同 | 对照有证据的状态、用户、窗体或选中对象条件；通用规则无需业务值，解释本次分支才按授权读取。 |
| 不明确的错误描述 | 先定位入口与可见证据，再按已发现的故障类型重新搜索并读取 Skill；不要持续使用兜底流程跳过专门诊断。 |

一个问题同时包含多个动作时，先围绕用户要解释的结果追踪，再说明与之相关的前置步骤。仍无法定位对象时只询问决定入口的必要信息，不扫描全组织组件。

## 停止条件

已确认入口、主要条件和可见业务效果；动态分支或缺失工件作为未知项保留，不为追求“全面”扫描无关组件。

源码可说明可能路径，不能证明某次实际执行。静态配置、实时值和录制信息的采集时间不同，出现冲突时说明时间与范围，不能把旧快照作为当前配置。

## 回答要求

先说明业务效果和触发条件。除非用户明确询问技术实现，否则把函数名、逻辑名和节点编号留在技术依据中。

给出与结论直接对应的证据和未知项，不强制固定栏目。完成前调用 `check_diagnostic_progress`；若相关代码缺失，说明需要补采的具体组件，不以必查工具已调用冒充解释完整。
