## 取证顺序

先按当前实体元数据确认字段逻辑名与具体控件，核对窗体标识。确认当前 FormXML 中控件是否静态禁用，再追踪窗体加载和字段变更事件。发现 `setDisabled` 或项目封装时，读取对应函数及实际条件；不要仅凭搜索关键词命中认定它控制当前字段。

## 条件分支

- 问题依赖本次控件状态或当前值且用户已授权时，读取目标字段的实时值、`isDirty` 和控件 `disabled` 状态。只解释静态锁定规则时无需读取业务值；工具可用不代表本题必须读取。
- 只有判断条件依赖数据库值时，才额外查询必要字段。
- 静态配置和脚本均未禁用时，把字段安全、记录状态或权限列为待验证项，而不是直接归因。

## 场景与处理

| 现象 | 处理方式与判断边界 |
| --- | --- |
| 正文可改、表头不可改 | 逐个核对 controls 中的控件名、禁用状态及对应脚本；表头、正文和流程控件不能互相代表。 |
| 选择状态后突然只读 | 追踪 OnChange 的条件及选项值映射，检查后续函数是否重新启用或再次禁用。 |
| 整张窗体不能编辑 | 检查窗体类型、记录状态、批量禁用封装和可见权限证据；单字段 disabled 不能证明整张窗体的原因。 |
| 只有部分用户不可改 | 对照已采集的角色条件、字段安全或更新权限；读取被拒绝不能等同于字段值为空。 |
| 计算字段或快速查看内容不能改 | 依据元数据和控件类型确认字段性质及来源记录；不把派生显示直接当成普通输入控件。 |
| disabled 为 false 仍无法输入 | 检查控件类型、业务规则、自定义组件和实际窗体是否一致；当前工具未采集的遮罩或 DOM 状态作为缺口。 |

若只读由 `setSubmitMode('never')` 等配置引起，应核对实际设置代码与运行时 submitMode；不直接调用 setDisabled(false)、修改字段安全或改变记录状态来验证。

## 停止条件

已确认静态禁用或脚本条件时解释来源及生效条件；只取得运行时控件状态时仅确认现象，并说明仍缺设置来源、字段安全或权限证据。给出对应的配置/代码核对点，不建议无证据地解除所有限制。完成前调用 `check_diagnostic_progress` 并保留证据缺口。
