## 取证顺序

确认预期变化的字段或关联记录、操作入口及观察时间。沿前端动作确认写入目标实体、记录 ID、字段和调用方式，区分仅修改窗体内存、提交保存、服务端写入和界面重新显示。

证据链落到当前实体写入时调用 `list_current_entity_plugin_steps`，核对阶段、同步模式、过滤字段和可能的二次更新；写入目标来源跨实体且未知时，在环境代码库可用的条件下重新匹配 `reverse-entity-writer`。不要以当前实体步骤清单解释所有关联实体的写入。

## 条件分支

- 没有写入调用证据时，结论限定为“未确认发起写入”。
- 存在失败响应时，区分写入被拒绝与事务回滚。
- 写入成功后值不同，检查后续同步/异步逻辑覆盖和界面刷新。
- 只有答案依赖实际值时，才按授权查询当前记录的必要字段。

## 场景与处理

| 现象 | 处理方式与判断边界 |
| --- | --- |
| 页面有新值，保存后恢复 | 授权后读取目标字段的 isDirty、submitMode 及必要条件值；检查 setSubmitMode('never') 和保存后的刷新，不能先认定插件覆盖。 |
| setValue 后没有联动 | 跟进 OnChange 绑定及是否显式调用 fireOnChange；setValue 本身不触发 OnChange，也不等于已保存。 |
| 数据库已更新，页面仍旧 | 对比同一记录、同一字段的实时值与已保存值及读取时间，核对刷新/回调路径；不自动刷新以免影响未保存内容。 |
| 提示成功但实际没写入 | 检查提示位置、业务返回码、实际写入调用和目标 ID；没有请求体不能据静态赋值断言本次提交了该列。 |
| 更新后一段时间被改回 | 查后续同步/异步写入的关联证据；最终值、modifiedon 或任意最近日志不能单独证明覆盖者。 |
| 主记录成功、关联记录没生成 | 确认跨实体调用、查询为空、重复检查和异步任务边界；代码库无覆盖时说明缺失的来源。 |

查询数据库当前记录时，`query_crm_data` 使用 `current_record: true`；其他关联记录使用已确认的关系或 ID 限定，select 只含必要字段。权限拒绝、字段缺失、null 和未采集是不同状态，不能互相替代。

同步 PostOperation 仍可能在事务内，不能因“后操作”就排除回滚；异步任务与原事务分开，任务失败不等于原保存被撤销。只有任务关联和状态可读取时才判断是否等待、失败或完成。

## 停止条件

把问题归入未发起写入、写入失败、事务回滚、后续覆盖、异步未完成、界面未刷新或证据不足之一。不能仅根据最终页面值断言服务端没有执行。

建议与已确认类别对应：补采提交链、核对提交模式、检查关联异步任务或验证显示刷新；不执行更新、重试任务或刷新页面。完成前调用 `check_diagnostic_progress` 并保留 evidenceGaps。
